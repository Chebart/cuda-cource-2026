Конфликт банков: зачем добавлять пустой столбец?

Читаем первый столбец тайла 32×32 (куска матрицы) из shared memory. Хотим получить [0, 32, 64, …, 992] в обеих версиях. Во второй добавим по пустой ячейке в конец строки: числа не поменяются, но будут лежать по другим адресам.

Что делает каждый блок

Строка 20: соседние потоки пишут в соседние ячейки строки. Каждый блок читает свой кусок входа.

Строка 22: первый столбец заполняет поток 0, а читают его все. Барьер не даёт прочитать число до записи.

Строка 24: каждый поток берёт первое число своей строки. Читаем тот же столбец, но при шаге 33 вместо 32 числа попадают в другие банки.

Запуск: сколько времени экономит пустой столбец?

nvcc -std=c++17 -O3 -arch=sm_75 06_bank_conflict.cu -o bank_conflict
./bank_conflict

На схеме был один тайл. Для замера берём 1024: каждый блок обрабатывает свой. Вот вывод на Quadro RTX 6000:

Tiles: 1024
WIDTH=32: [0, 32, 64, ..., 992]; 4.92 us/launch; PASS
WIDTH=33: [0, 32, 64, ..., 992]; 4.45 us/launch; PASS

Сверь числа в обеих строках: [0, 32, 64, ..., 992]. Это часть первого столбца первого тайла. Последнее число берём из строки 31: 31 * 32 = 992. Пустой столбец добавили справа, а читаем по-прежнему первый. Проверяем первый столбец каждого тайла.

Почему выигрыш около 10%? Чтение tile[lane][0] теперь идёт по разным банкам. Но каждый блок всё так же загружает 1024 числа из глобальной памяти, пишет их в shared memory, ждёт у барьера и записывает ответ. Весь запуск занял на 0,47 мкс меньше. Копируем и проверяем ответ уже после замера.

Дополнительно: как увидеть конфликт банков и проверить гонки

Запусти профилировщик на одном тайле:

ncu --csv --launch-count 2 \
  --metrics l1tex__data_pipe_lsu_wavefronts_mem_shared_op_ld.sum,l1tex__data_pipe_lsu_wavefronts_mem_shared_op_st.sum \
  ./bank_conflict 1

Сначала посмотри на счётчик чтения (op_ld.sum в конце имени). При ширине 32 видим 32 порции работы (wavefronts), при 33 — одну. Потом сравни запись (op_st.sum): по 32 в обеих версиях, потому что записываем те же 32 строки.

А если замерить весь запуск с одним тайлом (./bank_conflict 1 без профилировщика), в обеих версиях выходит около 2,4 мкс.

Racecheck смотрит не на банки, а на гонки. Например, не прочитал ли поток ячейку раньше, чем сосед в неё записал число. Отступ помогает банкам работать параллельно. Барьер нужен, чтобы не читать до записи.

compute-sanitizer --tool racecheck --launch-count 2 \
  --error-exitcode 99 ./bank_conflict 1

В конце посмотри на сводку Racecheck: в этом примере ожидаем 0 hazards.
