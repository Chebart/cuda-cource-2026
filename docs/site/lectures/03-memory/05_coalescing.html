Удваиваем x: массив векторов или отдельный массив?

Удваиваем x у 4 194 304 векторов. В одной версии читаем x из массива векторов, в другой — из массива, где лежат только x. Ответ одинаковый. Сравним время всего ядра: чтение, удвоение и запись.

Где лежат значения x?

У каждого вектора четыре координаты: x, y, z, w. В этом примере потоку нужна только x.

Массив векторов (AoS)

Потоки читают vectors[i].x. Между соседними x — 16 байт.

x0y0 z0 w0x1y1 z1 w1x2…

Отдельный массив на координату (SoA)

Потоки читают x[i]. Между соседними x — 4 байта.

x0x1x2…

[y0, y1, …] · [z0, z1, …] · [w0, w1, …] — отдельные массивы. Ядру передаём только x.

Подробнее: откуда в структуре пустые байты

Выравнивание говорит, с какого адреса можно начать хранить число. Обычно адрес float должен делиться на 4. Поэтому в struct { char tag; float x; } после первого байта пропускаем ещё три, чтобы x начался с байта 4. Эти пустые байты — padding:

tag · байт 0пусто · байты 1–3x · байты 4–7

С пустыми байтами выходит 8 байт на запись. На практике размер проверяем через sizeof, выравнивание — через alignof, смещение поля — через offsetof. В нашем Vector4 четыре float лежат подряд: по 4 байта на поле, всего 16 байт.

Адрес от cudaMalloc выровнен как минимум на 256 байт, поэтому начало массива совпадает с границей 32-байтного сектора. А если начать с x + 1, те же 32 float займут байты 4–131: получим уже 5 секторов вместо четырёх.

Подробнее: почему при транспонировании запись отличается от чтения

Пусть соседние потоки берут разные col в одной строке row. В out[col * height + row] = in[row * width + col] читаем соседние числа, но пишем уже в разные строки, с шагом height × sizeof(float) байт. Запись затрагивает больше секторов, как чтение x в AoS. Поэтому смотрим на чтение и запись отдельно. Чтобы поменять порядок обращений, можно использовать тайл в shared memory.

Чем отличаются две строки чтения

Строка 16: берём x из вектора. Строка 21: берём x из отдельного массива. Умножение и запись результата одинаковые.

Ставим отметки CUDA Events до и после 100 запусков одного ядра. В строке 82 уже после замера проверяем на CPU, что в каждой ячейке получилось 2*x.

Запуск: одинаковый результат, разное время

nvcc -std=c++17 -O3 -arch=sm_75 05_coalescing.cu -o coalescing
./coalescing

Пример вывода на Quadro RTX 6000:

AoS: [2, 4, 6, ..., 8192]; 147.13 us/launch; PASS
SoA: [2, 4, 6, ..., 8192]; 61.79 us/launch; PASS

Откуда 8192 в конце массива? На входе числа от 1 до 4096 повторяются. Последнее — 4096, его и удваиваем. Печатаем первые три числа и последнее, а для PASS проверяем весь массив.

us/launch — среднее время одного запуска в микросекундах. С SoA получили 61,79 мкс вместо 147,13 мкс. Вспомним схему: warp читает те же x из 4 секторов вместо 16. Умножение и запись те же. Данные готовим до замера, а ответ копируем на CPU и проверяем после.

Дополнительно: сколько секторов затронули и сколько байтов прочитали

Nsight Compute разберём в следующих лекциях. Здесь просим его снять счётчики с первых двух запусков: одного AoS и одного SoA.

ncu --csv --launch-count 2 \
  --metrics l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum,dram__bytes_read.sum \
  ./coalescing

Найди счётчик секторов при чтении (имя заканчивается на global_op_ld.sum) и сверь со схемой: на один warp было 16 секторов для AoS и 4 для SoA. Умножь каждое число на 131 072 — столько warp обрабатывают весь массив. Получишь 2 097 152 и 524 288 секторов.

dram__bytes_read.sum показывает, сколько прочитали из DRAM: около 64 и 16 МиБ. Секторов для чтения стало вчетверо меньше. Выигрыш по времени меньше: замер включает всё ядро, в том числе запись тех же результатов.
